# Архитектура Multi-Tenant LMS платформы

## 1. База данных и схема миграций

### Базовая миграция (init_postgres / 0_init)
- База данных: PostgreSQL 16+.
- Вся структура схемы приведена в соответствие с PostgreSQL через базовую миграцию `prisma/migrations/20261009180000_init_postgres`.
- Запрещено использовать `$queryRaw` и `$executeRaw` без принудительной фильтрации `centerId`.
- Порядок миграций отслеживается Prisma Migrate. При развёртывании выполняется команда:
  ```bash
  npx prisma migrate deploy
  ```

## 2. Модель изоляции арендаторов (Multi-Tenancy)

### `requireTenantAccess` и `getTenantDb`
- **Инкапсуляция тенанта:** Все операции с данными конкретного учебного центра внутри API и серверных компонентов обязаны выполняться через `tenantCtx = await requireTenantAccess(req)` (или `requireTenantPageAccess()`).
- **Безопасная БД тенанта:** Контекст предоставляет `tenantCtx.getTenantDb()`, который оборачивает Prisma Client через расширение (`src/lib/db-tenant.ts`):
  1. Автоматически инжектирует `centerId` во все запросы (`findMany`, `findFirst`, `create`, `updateMany`, `deleteMany`, `upsert`, `count`).
  2. Запрещает модификацию поля `centerId` у существующих записей.
  3. Проверяет foreign relations (внешние ключи) на принадлежность текущему тенанту (DMMF-валидация).
  4. Приостанавливает операции записи (`CENTER_SUSPENDED_WRITE` / 403), если учебный центр находится в статусах `PAUSED`, `BLOCKED` или `CANCELLED`.
  5. Для роли `PLATFORM_SUPPORT` активирует строгий режим `readOnly` (любая попытка записи бросает исключение на уровне Prisma Client).
- **ESLint Guard:** Прямой импорт `@/lib/db-tenant` запрещён глобальным правилом `no-restricted-imports` в `.eslintrc.json`, гарантируя, что разработчики используют только `requireTenantAccess`.

## 3. Где остался сырой `db` (`@/lib/db`) и почему

Прямой импорт глобального экземпляра Prisma Client (`import { db } from "@/lib/db"`) разрешён и используется **исключительно** в следующих категориях сервисов:

1. **Глобальная аутентификация и сессии (`src/app/api/auth/**`):**
   - Пользователь системы (`PlatformUser`) существует на уровне платформы и может быть зарегистрирован в нескольких центрах одновременно.
   - Поиск пользователя по email, проверка паролей, отзыв токенов сессий (`UserSession`), подтверждение почты (`emailVerificationToken`) и сброс пароля происходят **до** того, как определён активный арендатор (центр).
2. **Панель супер-администратора платформы (`src/app/api/platform/**`, `src/app/api/developer/**`):**
   - Управление списком учебных центров (`LearningCenter`), изменение директоров, заморозка/активация центров, системные аудит-логи и статистика платформы оперируют над самими тенантами, поэтому требуют платформенного доступа.
3. **Первичное погашение инвайт-кода (`src/app/api/invites/redeem`, `accept`):**
   - До момента активации инвайта пользователь ещё не состоит в учебном центре. Код проверяется глобально по таблице `InviteCode`, после чего создаётся запись в `CenterMembership`.
4. **Системные проверки жизнеспособности (`/api/health`):**
   - Проверка соединения с PostgreSQL `db.$queryRaw("SELECT 1")` без привязки к организациям.
